# Chrome has no 50MB model feature, so build your own

**Chrome has no feature, origin trial or intent with a 50MB model-size limit for developer-shipped models.** The research checked the Chrome built-in AI docs, blink-dev intents and the related explainers, and no 50MB figure appears in any of them. The figure is probably misremembered, or it comes from a general rule of thumb for "small" web models. Three real features come closest. **Cross-Origin Storage (COS)** is a shared, hash-keyed model cache that reached Intent to Prototype in August 2026. **WebNN** runs custom models and is in origin trial from M147 to M149, with Android excluded. The **Prompt API polyfill** puts your own local or cloud backend behind the Prompt API shape. Chrome's built-in Gemini Nano APIs run only a Chrome-managed model of several gigabytes, on desktop only, and you cannot bring your own weights. For an Android-first personal-finance PWA, the practical path today does not need any new Chrome feature. Ship a small quantized model (about 23 to 28MB) with Transformers.js, LiteRT.js or MediaPipe. Run it on WebAssembly everywhere, speed it up with WebGPU where the device supports it, and cache it with the service worker and persistent storage.

## The 50MB limit traces back to no Chrome source

The COS Intent to Prototype gives no size limit in MB or GB, and it names "multi-gigabyte AI models" as the main reason the feature exists ([blink-dev I2P](https://groups.google.com/a/chromium.org/g/blink-dev/c/p5nq70aN63o/m/uNm_oaEOBQAJ)). The COS explainer calls per-origin storage limits **"implementation-defined"** and defines `QuotaExceededError` without giving a number ([WICG explainer](https://github.com/WICG/cross-origin-storage)). The built-in AI track sits at the other end of the scale: the Gemini Nano model is **about 4GB on disk**, and Chrome requires about 20GB of free space before it downloads it ([Chrome Help](https://support.google.com/chrome/answer/16961953?hl=en); [DEV investigation](https://dev.to/jacquesgariepy/inside-chromes-edges-silent-4gb-ai-install-a-complete-hands-on-investigation-54g2)). The only small concrete size in the Transformers.js and COS coverage is the ONNX Runtime Wasm file, at about 4.7MB ([getaibook](https://getaibook.com/news/chrome-brings-cross-origin-model-caching-to-transformersjs)).

Two caveats apply. The researchers did not read the last part of the COS explainer or the live chromestatus pages, so a size figure there cannot be fully ruled out. Even so, nothing found points to a 50MB rule, and nothing in Chrome stops a page from loading a 50MB model with ordinary web APIs today.

## Three real features each cover one piece of the problem

The closest features split the job into storage, inference and API shape. No source presents them as one product.

| Feature | What it does | Status (Nov 2026) | Android |
|---|---|---|---|
| Cross-Origin Storage | Shares model files across sites, keyed by SHA-256 hash | Intent to Prototype, Aug 18, 2026; flag or extension only | Not shipped |
| WebNN | Runs custom models on CPU, GPU or NPU | Origin trial M147 to M149 | Excluded (CPU only so far) |
| Prompt API polyfill | Prompt API calls routed to your own local or cloud backend | Experimental | Works where your backend works |
| Built-in Prompt API (Gemini Nano) | Chrome-managed model, text, image and audio input | Stable on the web from Chrome 148 | Not supported |

**Cross-Origin Storage** is a storage layer. A page calls `navigator.crossOriginStorage.getFileHandle({algorithm:'SHA-256', value:'<hex>'}, {create, origins})` and gets back a `FileSystemFileHandle`. If the file is missing it gets `NotFoundError` and fetches from the network; a hash mismatch returns `DataError` ([WICG explainer](https://github.com/WICG/cross-origin-storage)). Files are keyed by hash, so the format does not matter: ONNX, `.tflite` or GGUF all work, and the runtime decides what it can read. Privacy controls include a Public Hash List for globally shared files, deliberately noisy "absent" answers, and a budget of about 8 to 16 cross-site lookups per window. The explainer says the API is **"not yet natively implemented in browsers"** and that testing uses an extension that injects a polyfill ([Chrome Web Store extension](https://chromewebstore.google.com/detail/cross-origin-storage/denpnpcgjgikjpoglpjefakmdcbmlgih)). Transformers.js v4.2.0 added experimental support on June 23, 2026, turned on with `env.experimental_useCrossOriginStorage = true`. It checks COS first and falls back to the Cache API or the network ([getaibook](https://getaibook.com/news/chrome-brings-cross-origin-model-caching-to-transformersjs)). For a single personal app, COS adds little: its value is that two different sites can reuse one download of the same model.

**WebNN** is the inference layer that would reach NPUs. Its origin trial was planned for M146 to M148, delayed by release-blocking issues, then re-enabled from M147 through M149 **with Android excluded** because the Android implementation is CPU only ([blink-dev Intent to Experiment](https://groups.google.com/a/chromium.org/g/blink-dev/c/5CWKSChYo98/m/9mwAcwz3AAAJ); [Android exclusion](https://mid.mail-archive.com/blink-dev@chromium.org/msg15857.html)). Whether WebNN moved to Intent to Ship after M149 is unverified.

**The built-in Gemini Nano APIs** are a separate, managed track. Chrome downloads the model and maintains the LoRA weights for task APIs, and pages cannot supply their own ([Model management](https://developer.chrome.com/docs/ai/understand-built-in-model-management)). The Prompt API is stable for web pages from Chrome 148 on Windows, macOS, Linux and Chromebook Plus. **Android and iOS are "not yet supported"** ([Prompt API](https://developer.chrome.com/docs/ai/prompt-api)). The hardware bar is desktop class: 22GB free disk plus a GPU with more than 4GB of VRAM, or 16GB of RAM and 4 CPU cores ([Get started](https://developer.chrome.com/docs/ai/get-started)). "Gemini in Chrome" on Android, which reached US users in August 2026, is a cloud assistant and not a web API ([Google blog](https://blog.google/products-and-platforms/products/chrome/bringing-chrome-ai-to-android/)). The **Prompt API polyfill** keeps the same API shape but lets the developer register a cloud or local backend ([Prompt API polyfill](https://developer.chrome.com/docs/ai/prompt-api-polyfill?hl=en)). That makes it a useful wrapper if you later want to use Gemini Nano on desktop and your own model elsewhere.

## Four runtimes already ship small models to Android Chrome

The working stack in late 2026 uses existing APIs. **Transformers.js v4** runs on ONNX Runtime Web with a new C++ WebGPU runtime and about 200 architectures. Its ModelRegistry API can list, check and clear cached model files, and `env.useWasmCache` keeps the runtime files available offline ([HF blog](https://huggingface.co/blog/transformersjs-v4)). Secondary sources say a plain `npm install` still resolves to v3, so v4 needs the `@next` tag; check this before adopting it ([GitHub releases](https://github.com/huggingface/transformers.js/releases)). **LiteRT.js**, announced July 9, 2026, replaces TensorFlow.js for `.tflite` models with CPU (XNNPACK), WebGPU and experimental WebNN backends ([Google Developers Blog](https://developers.googleblog.com/en/litertjs-googles-high-performance-web-ai-inference/)). **MediaPipe Tasks** offers ready-made tasks such as a MobileBERT text classifier ([MediaPipe text classifier](https://developers.google.com/edge/mediapipe/solutions/text/text_classifier)). **WebLLM** runs MLC-compiled chat models on WebGPU, including SmolLM2-135M builds ([HF mlc-ai](https://huggingface.co/mlc-ai/SmolLM2-135M-Instruct-q0f16-MLC)).

The accelerator story favours Android more than the built-in AI story does. **Chrome 121 turned WebGPU on by default for Android 12+ devices with Qualcomm or ARM GPUs**, Chrome 127 added an experimental OpenGL ES backend, and Chrome 146 added an opt-in compatibility mode on OpenGL ES 3.1 ([Chrome 121](https://developer.chrome.com/blog/new-in-webgpu-121); [Chrome 146](https://developer.chrome.com/blog/new-in-webgpu-146)). Safari 26 also ships WebGPU on iOS ([web.dev](https://web.dev/blog/webgpu-supported-major-browsers)). WebAssembly works everywhere as the fallback.

Several useful models fit well under 50MB:

| Model | Size | Good for |
|---|---|---|
| all-MiniLM-L6-v2 (int8 ONNX) | 23MB (fp16 45.3MB, fp32 90.4MB) | Embeddings, similarity, category suggestions |
| MobileBERT classifier (quantized) | About 28MB | Text classification, fine-tunable with Model Maker |
| Whisper-tiny (int8) | About 60MB for one community build | Voice entry; at or over the limit |
| SmolLM2-135M (4-bit) | Near the limit, sizes unverified | Simple generation only, no reasoning |

Sources: [HF MiniLM files](https://huggingface.co/Xenova/all-MiniLM-L6-v2/tree/main/onnx); [MediaPipe customization](https://developers.google.com/edge/mediapipe/solutions/customization/text_classifier); [whisper-tiny-uz-onnx](https://huggingface.co/davron112/whisper-tiny-uz-onnx).

Performance data for phones is the biggest gap. Desktop benchmarks from early 2024 show MiniLM at sequence length 512 taking **about 386ms on WASM versus about 23.8ms on WebGPU** on a Mac ([HF benchmark](https://huggingface.co/spaces/Xenova/webgpu-embedding-benchmark/discussions/4)). The researchers found no reliable mid-range Android numbers. One developer reported that a mobile browser capped WebGPU buffers at 128MB when running SmolLM2-360M, forcing a shorter context ([DEV](https://dev.to/garciadiazjaime/running-language-models-directly-in-the-browser-2c3e)). Expense descriptions are short, usually under 32 tokens, so a 23MB MiniLM on WASM is likely fast enough on phones. That is an inference, and it should be measured on target devices.

## A 25MB classifier fits an Android-first expense PWA today

For this app, the best first feature is **category suggestion**. Embed each new expense description with int8 MiniLM (23MB) and compare it with the user's past categorised expenses. Alternatively, fine-tune a small classifier on the user's own categories. Either runs fully on the phone, so descriptions and amounts never leave the device. Tiny LLMs are a poor fit for receipt reading: dedicated OCR or vision models do that job better, and this project already reads receipts through its Docling service.

Storage needs care on phones. Browser storage is best-effort by default, and Chromium evicts the least recently used origin first when disk runs low, although one origin may use up to 60% of the disk ([web.dev storage](https://web.dev/articles/storage-for-the-web)). Call `navigator.storage.persist()` after the user does something meaningful, not on page load ([web.dev persistent storage](https://web.dev/articles/persistent-storage)). Precache the model in the service worker so the feature works offline, and handle `QuotaExceededError` on cache writes ([MDN](https://developer.mozilla.org/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)). On iOS, Safari's 7-day storage cap does not apply to home-screen PWAs, so offline use there depends on installation. A 23MB download takes a few seconds on 4G and loads from cache after that.

On desktop, the Prompt API is an optional extra. It accepts images and returns JSON that matches a schema through `responseConstraint` ([Prompt API](https://developer.chrome.com/docs/ai/prompt-api)). Check `LanguageModel.availability()` and fall back to your own model when it is missing. Do not make it the only path: the model can be evicted at any time, its version cannot be pinned, and it supports only English, Japanese, Spanish, German and French.

## Conclusion

The question assumed a single Chrome feature for shipping small models, and the real picture is more useful than that. Small models are already a solved problem on the web with WASM and WebGPU, while Chrome's new work targets the opposite end: multi-gigabyte models that need a shared cache (COS) or managed delivery (Gemini Nano). For an Android-first app, every new Chrome AI feature found either excludes Android or is not yet shipped, so waiting for one buys nothing.

The practical decision is to build on Transformers.js or LiteRT.js now, keep the model at 25MB or less so the WASM fallback stays usable on cheap phones, and put the model behind a small interface (the Prompt API polyfill is one option). That leaves room to adopt COS or WebNN later without rewriting the app. The first job is to measure: run a MiniLM benchmark on the two or three Android phones your users actually have.
